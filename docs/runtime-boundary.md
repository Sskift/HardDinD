# 当前运行边界与未解决的问题

用户最新目标是在 Starpub 现有无特权容器内支持几乎所有 Docker 命令，效率与原生相差不大；此前提出的 GPU 仍在范围内。当前实现没有达到这个目标，具体的性能容差也尚未约定。不能把微基准加速或部分命令成功写成已交付。

这里实际修改的是独立的 Linux 7.2.10 UML 内核，它以宿主进程运行。Starpub 正在运行的宿主内核仍是 5.15.0-177-generic。编辑源码、编译 UML 和替换宿主正在运行的内核是不同操作；容器内的 root 不具有替换宿主内核所需的权限。

`run-host-probes.py` 以容器内 root 分别测试了 `unshare`、`clone`、`clone3`，每次尝试都在独立子进程中完成。普通 `clone` 可以创建进程，带 user/mount/network/PID/cgroup namespace 标志的 `clone` 返回 EPERM，`clone3` 返回 ENOSYS。`unshare` 同样被拒绝。`host-probes.json` 同时记录进程的 capability 和 seccomp 状态。不能把 `unshare` 失败直接推断成所有入口失败，因此这些入口是分别实测的。

Moby、containerd 和 runc 的源码可以修改，但删除它们的权限检查不会改变宿主系统调用的结果。获得正常 Docker API 响应，也不等于 namespace、文件系统、网络和资源隔离已经执行。

UML 能在自己的内核中实现 Linux namespace、cgroup、overlayfs 和网络，因此原版 dockerd 的一部分实际功能已经运行成功。这没有证明完整兼容，更没有证明性能一致。默认补丁和第一个实验处理内核与用户进程之间的交接；新的独立实验处理同一地址空间的并行线程。它们没有跳过 guest 系统调用语义，完整 GPU 后端仍未实现。

同一地址空间的线程串行化来自 `arch/um/kernel/skas/mmu.c` 的 `turnstile` 和 `arch/um/os-Linux/skas/process.c` 的用户态执行循环。删除锁会让不同线程同时修改同一份寄存器、信号栈和请求数据。正确实现需要独立线程状态、共享地址空间、TLB 更新同步、信号与退出处理；只把 `ncpus` 调大或删锁不能作为实现。

`0003-um-shared-vm-runners.patch` 已实现并行原型：每个 `mm` 保留一个只处理映射和克隆的宿主进程，为每个使用该地址空间的虚拟 CPU 延迟建立独立执行进程。执行进程用 `CLONE_VM | CLONE_PARENT` 共享宿主页表，文件表、信号栈和寄存器分别维护；执行期间固定虚拟 CPU。映射队列受锁保护，页表快照使用原子比较更新，避免覆盖并发页表变化。负向 TLB flush 同步完成，防止解除映射、收紧权限和 fork/COW 后继续使用旧宿主映射。

这个原型在 Starpub 实测通过 TLS、迁移、锁、权限撤销、解除映射、重映射、并发 fork/COW、线程反复创建退出，以及 Docker 内的同组测试。保留的旧内核和新内核关闭实验的路径都复现了 COW 检查失败。对照中并行纯计算加速明显，系统调用和进程创建仍有数量级差距；参见 [原始结果](../results/starpub-2026-10-14-threads/)。

这不是生产级线程后端：宿主执行进程异常退出、分配失败和长期内存压力的覆盖仍不足；部分失败路径会终止整个实验 guest。上游 seccomp stub 已存在共享物理内存和信号控制方面的内部隔离缺口，多个执行进程共享 stub 区域后还需要重新审计，不能将当前原型用于不受信任的工作负载。这里没有把“测试通过”扩大成隔离保证。

后续性能实验继续使用完整的 guest 系统调用分发，包括 guest seccomp、ptrace、信号与资源控制。按需唤醒使用原子发布和睡眠标记；空映射快路径只有在脏范围和待执行命令都为空时才跳过同步锁，实际撤销映射仍在返回前完成。映射管理进程只保留不随应用变化的物理内存 FD，应用执行进程关闭它；这一优化没有解决上述内部隔离缺口。

可选缓存最多保留 4 个空闲映射管理进程及其各 2 页数据。归还前销毁全部执行进程，清除应用区和所有执行进程栈的宿主映射，再同步确认完成；缓存进程继续加入退出追踪，并在关机时清理。归还时清理失败的进程直接销毁；已经死亡的缓存项不会复用，其资源在关机时回收。每次复用仍建立新的执行进程，不能靠继承旧应用寄存器或跳过地址空间清理来加速。

扩大到多个线程同时 fork/exec 后，上一版并行基线出现过一次宿主进程丢失并导致 guest panic。失败记录必须保留；随后完整重测通过不等于修复已获证明。新版本增加宿主退出状态和 stub 错误码，以便继续定位偶发失败。完整性能验收仍需要控制宿主负载、应用级存储与网络对照及长期压力，不能由几项中位数代替。

GPU 仍有未完成的工程工作。可选的 [mapping-v14 内核](../results/starpub-2026-10-15-candidate-review/gpu-mapping-v14/README.md) 已让内部 Docker 在四张 A100 上顺序执行真实 CUDA 计算、双向传输和逐元素校验，前后原生对照也通过。随后普通运行暴露 CUDA 304/999 和异常退出；[完成交接修复](../results/starpub-2026-10-15-candidate-review/gpu-completion-v1/README.md) 纠正了同步操作提前完成下一条异步请求的竞态，开启异步等待的八组四卡对照通过，包含无追踪运行。长期稳定性仍须扩大验证。当前成功实测用显式设备传入及固定驱动库镜像；标准 `docker run --gpus all` 接入尚未完成，并发进程/线程、扩展显存生命周期和性能仍须验证。后端需要处理 NVIDIA ioctl 的内嵌指针和文件描述符、设备 mmap、UVM 与进程地址空间、锁页内存和退出清理。复制设备节点、导入驱动库镜像、在外层代跑测试都不能替代这些语义。

新的[共享地址空间 GPU 原型](../results/starpub-2026-10-14-gpu-broker/) 验证了实现接入所需的两项约束：单个独立进程或同 TGID 的两个线程处理全部 NVIDIA ioctl/mmap 时，外层真实四卡计算通过；同一份二进制切换到两个不同 TGID 的进程后，CUDA 上下文创建返回 800。普通 NVIDIA 设备的第二映射成功，UVM 第二映射均返回 EINVAL。v6 又在不共享 mm 的子进程中重新建立 124 个普通设备映射，4 个 UVM 映射仍失败；子进程继承文件引用和初始地址空间，未读写新映射，不能直接认定独立 UML 内核访问已可用。UVM 固定版本源码要求地址等于文件偏移，原型的任意地址别名违反这一约束，不能把其 EINVAL 泛化为所有跨 mm 方案均不可行。

后续 [0012 控制通道](../results/starpub-2026-10-14-gpu-control/) 已在实际 UML 内核创建专用宿主进程，转接固定控制设备的文件引用并在共享 mm 中处理平面 ioctl；guest 和内部 Docker 的版本查询与生命周期子集通过。控制节点默认关闭；目前一个 mm 仅绑定一个 guest 线程组，跨组使用返回 EXDEV，等待时关闭当前 guest CPU 中断，因此尚不能开放阻塞 CUDA 命令。后续 [0013 描述符关联](../results/starpub-2026-10-14-gpu-fd/) 已实现 REGISTER_FD 的嵌入 FD 转换，并修复实测发现的通用用户内存读取权限缺陷；其他内嵌 FD/指针、设备 VMA、UVM 缺页、锁页内存和内部 CUDA 仍未实现，GPU 验收仍失败。

评估过的现成替代也不能直接声明达标：gVisor 提供 nvproxy，但它支持的驱动版本和设备接口有明确范围；其 Docker-in-gVisor 文档还要求关闭 dockerd 的 iptables/ip6tables 并调整网络配置。它可作为实现参考，不能直接替换完整 Docker 的目标。参见 [gVisor GPU 支持](https://gvisor.dev/docs/user_guide/gpu/) 和 [Docker in gVisor](https://gvisor.dev/docs/tutorials/docker-in-gvisor/)。

验收保持失败。当前资料支持的结论是：这些补丁可以继续研究和测量，但没有可交付的“完整功能、原生相同性能、GPU”实现。原生容器路线需要宿主实际允许所需的 namespace、挂载和资源控制；这超出当前固定运行条件。用户没有授权放宽目标，仓库也不把尚未实现或已失败的条件改成通过。
