# 采样器所在 cgroup 的对照

这次在 Starpub 用同一份阶段计时探针二进制 `afef800dc5c1…`、同一个 4 vCPU guest 和 cpuset 内核 `fb5e56e48240…`，实际执行四组各 50 次的采样。先运行两组无忙线程的采样，再启动一个限额 0.5 核、含四个忙线程、持续 40 秒的容器；分别从另一个不限额容器和 `docker exec` 进入忙容器采样。两次观察的完整窗口均位于实际忙线程运行区间内。

| 采样位置与负载 | 最长单次采样 | 最长采样起点间隔 | 观察窗口内 throttled 次数增量 |
|---|---:|---:|---:|
| 单独采样，限额 0.5 核 | 1.345 ms | 102.296 ms | 0 |
| 单独采样，不限额 | 50.349 ms | 1351.754 ms | 0 |
| 忙线程在另一个限额容器，采样器不限额 | 1.132 ms | 101.807 ms | 0 |
| 采样器与忙线程共享 0.5 核限额 | 98.210 ms | 301.736 ms | 66 |

采样配置间隔为 100 ms，但 `capture-test` 在上一轮完成后再相对休眠，因此实际起点间隔也包含前次采样耗时。表中全部为观测值，没有套用性能通过阈值。

同一限额容器的观察窗口中，66 个计量周期均发生了节流；采样器自身增加 70 ms 的进程 CPU 时间。分离后的采样在这次运行中没有出现同样的长停顿，支持“观察者也会被被测容器的配额拖住”这一解释。但这是按固定顺序进行的一轮诊断，不足以唯一归因或估计发生频率。

不限额且没有忙线程的一组仍出现了明显延迟：最长采样主要落在第一次 `cpu.max` 的操作区间，约 50.020 ms，并被 guest 线程 CPU 时钟记为 50 ms；采样起点间隔最大 1.352 秒。该组没有新增节流记录。因此不能把所有停顿都解释为 CPU quota，也不能根据这份数据直接认定宿主抢占、IPI 或某个内核锁就是原因。它为进一步关联 guest 调度与宿主进程运行时间提供了可复查的反例。

所有命令正常结束，容器清单为空，guest 正常关机，输入哈希前后相同；独立检查的 18 个进程组全部为空。首次启动在导入 Python 依赖时失败，未创建 guest；补齐冻结的 `port_driver.py`、`result_checks.py` 后执行了上述唯一一次运行。原始异常、启动记录和修复后的完整源码均保留。

`report.json` 保留原始采样、命令和输入哈希，`analysis.json` 是独立重解析结果，`cleanup-audit.json` 是结束后检查。内核、磁盘、探针、网络后端及 Docker CLI 二进制仅保留远端路径和哈希，未复制进仓库；Python 依赖和探针 C 源码已经归档。原有 CPU limits 验收器没有因本次诊断修改。多次采样结果不等于完整 CPU 或性能验收。
