# Docker CPU 限制的实际执行验证

在 Starpub 现有无特权容器中，通过上游 Docker CLI 操作内部 Moby daemon。只读外层 cgroup；没有增加宿主权限或使用宿主 Docker socket。这里检验 CPU 限制是否生效，不是接近原生性能的验收。

## v1：确认 cpuset 被丢弃，整体失败

运行时间为 2026-10-15 北京时间 03:31–03:38，其中包含等待构建锁的时间。使用 4 vCPU guest，内核 SHA256 `9192f196143242aab3dfacc2966d7bcc605db9cc0caadfe68b09a76cb42b557e`，测试工具对应 `f38370c`。原始结果见 [report.json](v1/runtime/report.json)。

| 检查 | 原始判定 | 实际观察 |
| --- | --- | --- |
| 不限额，4 个忙线程 | pass | 线程总 CPU 时间约 3.97 核，cgroup 约 3.98 核，没有节流 |
| `--cpus 1` | pass | cgroup 约 1.014 核，60 次节流 |
| `--cpu-period=50000 --cpu-quota=25000` | indeterminate | cgroup 约 0.493 核；原判定器把工作线程约 0.477 核判为低于供给边界，未计入采样线程消耗 |
| `--cpuset-cpus=0` | fail | Docker 明确警告 cpuset 被丢弃；工作线程仍分布在 CPU 0–3 |
| `--cpuset-cpus=1-2` | fail | 同样被丢弃，工作线程仍分布在 CPU 0–3 |
| cpuset 0 与 `--cpus 0.5` 组合 | fail | quota 有节流，cpuset 被丢弃 |
| 同一容器 `docker update`：2 → 0.5 → 2 | pass / indeterminate / pass | cpu.max 与容器身份均有实际观察；中间窗口的 cgroup 约 0.502 核，探针进程约 0.473 核，原判定将观察开销当成供给不足 |
| CPU shares 竞争 | not_tested | 后续独立实验，不能计为通过 |

三个 cpuset 启动命令的 stderr 都包含 `Cpuset discarded`，`docker inspect` 中 cpuset 为空，容器内 `cpuset.cpus.effective` 返回 ENOENT。对应的 [实际内核配置](v1/baseline-kernel.config) 是 `# CONFIG_CPUSETS is not set`。这证明此前配置写入或命令退出码成功不足以证明限制功能可用。

该轮实例正常关机，没有强制关机。69 个命令进程组加 guest、网络辅助进程，共 71 个记录的进程组在独立检查时为空。[归档复核](v1/archive-audit.json) 用该轮冻结的原判定器重算固定阶段和动态更新阶段，结果与原报告完全一致；没有用后来的判定器覆盖旧结果。输入哈希、原始 stdout/stderr、运行器、探针、判定器和内核配置均已保存。

## 修复与待验证范围

内核配置补上 `CONFIG_CPUSETS=y`，新内核已重建并完成下述 v2 实测。

判定器的配额供给下限改为检查整个 cgroup 的 CPU 用量，因为配额也包含采样线程和 `docker exec` 观察进程的消耗。工作线程、进程与 cgroup 仍须满足原有计数一致性检查，所有计数仍须低于相同配额上限，同时要求实际节流、足够的不限额负载以及正确的 cpu.max。新增采样开销正例和无法解释的大额非工作线程消耗负例；33 个判定器测试在 Starpub 通过。该修正没有调整配额边界，也没有引入性能验收阈值。

GPU、多卡与显存生命周期、其他 Docker 命令、CPU shares 和接近原生性能仍分别需要完成。

## v2：cpuset 生效，整体仍为 indeterminate

内核 SHA256 `fb5e56e48240f96a997aa0f1d234992f128d23dd428eb8256dfccccc4d217fca`。补丁清单与 v1 完全相同，生成配置只增加 CPUSETS 及其 UNION_FIND 依赖，并保留 CPUSETS_V1 关闭。构建、配置与 [原始报告](v2/runtime/report.json) 已归档。

- CPU 0：所有四个线程的起止亲和性均为 `[0]`，实际运行 CPU 也只有 0。
- CPU 1–2：所有线程的起止亲和性均为 `[1, 2]`，实际运行 CPU 均在其中；两核占用判定通过。
- CPU 0 与半核 quota 组合：亲和性、实际运行 CPU 和 quota 节流均通过。
- 固定 `--cpus 1`、显式 50 ms 周期/25 ms quota、动态更新前后两个 2 核窗口均通过。
- 不限额参照、单核 cpuset 的计数一致性、动态更新的半核窗口仍为 indeterminate。全组不能算通过。

单核阶段工作线程总计约 0.913 核，进程/cgroup 约 0.991 核，原探针未独立记录采样线程的 CPU 开销。不限额阶段的最后一次采样在工作线程截止之后醒来，把已停止负载的尾部时间也计入参照。动态半核阶段的第一次 `docker exec snapshot` 到负载第 11.04 秒才输出，落在用于测量的半核窗口中；探针进程约 0.455 核、整个 cgroup 约 0.502 核，观察进程也争用配额。

后续探针增加采样线程 CPU 时钟和工作线程截止时间；计数一致性比较所有线程之和，原始工作线程与采样开销分开保存。不限额与纯 cpuset 的可供负载时段排除已知的截止后空闲尾部。动态调整直接使用忙进程持续读取的 cpu.max 证据，计量窗口内不再新建 `docker exec` 观察进程。没有扩大原有配额上限或一致性容差。相关 35 个单元测试及静态探针编译在 Starpub 通过，v3 实测结果如下。

v2 正常关机，71 个记录的进程组独立复核均为空。归档用 v2 冻结判定器重算所有阶段，与原报告一致；v1、v2 的原始无法判定项均保留。

## v3：固定阶段通过，动态半核窗口采样不足

使用相同 `fb5e56e...` 内核，加入采样线程 CPU 时钟与负载截止时间，并移除计量窗口内的额外 exec 观察进程。[原始报告](v3/runtime/report.json) 总体仍为 **indeterminate**，不是完整 CPU 验收通过。

当轮判定：不限额参照、`--cpus 1`、显式 quota/period、单核 cpuset、范围 cpuset、cpuset 与半核 quota 组合，以及动态更新两端的 2 核窗口通过。工作线程、采样线程、整个进程与 cgroup 的计时证据分别保留。此前 v2 的约 0.47 秒是进程与工作线程计时差额，不能当作独立测得的采样线程时间；v3 才增加这一独立时钟。

动态半核窗口只有 6 个采样点，固定丢弃前 5 个、后 2 个后没有可用区间，因此明确返回 indeterminate。另一个时序缺口也已找到：采样时间戳在 `read_cg()` 前记录，而它会读取五个 cgroup 文件；受配额限制的读取可能跨越一次更新，导致时间戳与实际读取的配置不在同一时刻。v3 中首次恢复 2 核配置的样本时间戳是 11.775 秒，控制端更新实际约在第 12 秒后执行。后续需精简采样、记录读取起止时间及配置稳定性，并按真实时间而非采样点数裁剪窗口。不能用缩小保护区或放宽一致性容差掩盖此问题；本轮“通过”仅表示原判定器结果，仍须完成采样时序修正后的复测。

v3 正常关机，67 个命令进程组及 guest、网络进程合计 69 个进程组独立检查均为空。35 个单元测试、严格静态编译、自检通过。归档重算与冻结报告一致，前两轮失败与无法判定项均未修改。

## v4：记录采样时间范围，仍未通过动态更新全组

在相同 cpuset 内核与基础磁盘上运行冻结的 v4 候选。探针改为用持久 FD 读取必要计数，记录每次读取前后的时间，先后两次读取 `cpu.max` 判断配置是否跨越更新；解析失败和首次读取错误均直接记录。判定器按时间选择稳定窗口，保留慢采样记录。该候选尚未替换主线探针与判定器。

[原始报告](v4/runtime/report.json) 为 **indeterminate，退出码 2**。六个固定阶段和初始 2 核更新窗口通过；动态半核与恢复 2 核窗口无法判定：

- 半核阶段有 18 个可用样本，端点之间约 5.840 秒；进程及 cgroup 均约 0.440 核，低于该时段原有 CFS 计量规则的 0.4786 核下界，59 次节流。这次已经不是没有可用样本，仍不能计为通过。
- 恢复 2 核后，选出的稳定内部窗口仅约 0.949 秒，未达到原有 1 秒要求；没有为了通过而降低要求。
- 单核 cpuset 阶段，有一次采样从相对时间 1.283 秒持续到约 6.002 秒，即 4.719 秒。该阶段的线程亲和性和总 CPU 用量检查仍通过，但长采样的具体阻塞位置需要进一步诊断。更新阶段也存在长间隔。

这些是原始数据能支持的观察，尚不能区分宿主调度、guest 任务调度、计时记账或具体读取阻塞。v4 作者交付报告中将旧版无时间范围的样本低速区间归因于宿主放置不足，证据不够；该报告仅保留为候选交付记录，此处不采纳其因果断言。guest 的 steal 为 0 也不能排除宿主进程被延迟调度。

另外，独立检查发现 v4 判定器的时间不确定性边界可能误报 FAIL：若计数增量为 0.635 秒、两个端点的读取分别耗时 20 ms，则实际计数间隔可以在 1.00–1.04 秒之间；半核配额在较长间隔下符合现有上界，但 v4 只按最短间隔判为超限。这类跨边界证据应该是 indeterminate，不能是 pass 或已证实违规。该反例针对实际冻结函数，可通过 [recheck.py](v4/recheck.py) 复现；它没有出现在本轮运行的判定结果中。修复继续进行，原始报告不会被覆盖。

运行前在 Starpub 独立执行的 99 个测试通过，静态探针编译和自检通过。实例正常关闭，67 个命令进程组及 guest/network 合计 69 组独立复查为空，输入哈希一致。[归档审计](v4/archive-audit.json) 从逐条压缩原始日志重新计算固定阶段和三个更新窗口，与原始报告完全一致。完整功能、CPU shares 竞争和接近原生性能仍未验收。

## v5：采样与判定修复合入主线

主线现在采用已在上述三轮实际运行的采样实现：持久 FD、每次读取的起止时间、两次 `cpu.max` 观察、首次错误保留和按时间选取稳定窗口。新判定器按采样区间的最短与最长可能时长分别计算上界：所有可能时长都超限才判 fail，所有可能时长都合规才允许继续检查通过条件，其余为 indeterminate。没有改变 CFS 记账常量或性能标准。

独立审查还补上三项一致性检查：固定阶段必须提供起止采样边界；稳定标记必须与两次 `cpu.max` 读数一致；顺序采样的时间范围不能互相重叠。旧候选曾在前两项证据被删除或篡改时仍通过，新的实际函数反例与测试会拒绝它们。旧格式的历史数据须使用各轮冻结判定器，不能假定缺失的读取时长为零。

最终源码在 Starpub 完成严格静态探针编译、实际文件读取反例及全部 **110 个测试，退出码 0**，见 [验证记录](v5-review/validation-result.json)。[独立重算脚本](v5-review/recheck.py) 用最终冻结源码从三轮原始日志重新计算 27 个阶段：v4 的两个 indeterminate 保持不变，B 与 A2 的九项各自仍通过；0.635 秒边界反例改为 indeterminate，明确超限与合规则分别保持 fail/pass。[重算证据](v5-review/reanalysis.json) 与原始报告分开保存。此处是测量工具修复，没有新增 runtime 或性能验收，也没有解决长采样停顿。

## 逐步计时诊断：停顿分布在多个读取位置

从已验证主线复制独立探针，为两次 `cpu.max`、`cpu.stat`、`/proc/stat` 和进程 CPU 时钟这五步增加起止时间，同时单独记录每步前后读取线程 CPU 时钟的耗时。诊断源码与运行器只保存在 [capture-v1/sources](capture-v1/sources/)，没有加入默认采样路径；额外观察成本意味着本轮不能作为性能提升证据。编译、自检、真实文件计时格式检查和 110 项测试通过后，在同一 cpuset 内核与磁盘上运行完整 CPU 限制矩阵。

[实际 Docker 报告](capture-v1/runtime/report.json) 的九个阶段均通过，退出码 0。逐步计时保留了以下长停顿：

| 阶段 | 一次完整采样耗时 | 其中的主要位置 |
| --- | ---: | --- |
| `--cpus 1` | 188.597 ms | 第二次 `cpu.max` 读取步骤约 188.141 ms |
| 显式半核配额、50 ms 周期 | 250.105 ms | `/proc/stat` 前的线程时钟计时区间约 248.029 ms；文件读取步骤只有约 0.127 ms |
| cpuset 1–2、无 quota | 323.934 ms | `/proc/stat` 读取步骤约 323.720 ms |
| 动态更新的半核阶段 | 300.843 ms | 两个读取步骤之后的线程时钟计时区间分别约 109.829 ms 与 189.875 ms；对应文件读取步骤均不到 0.21 ms |

这里的“读取步骤”包括相应系统调用与解析；墙钟区间也包含可能的调度等待，不能仅凭区间长就判定具体系统调用或内核锁有缺陷。长停顿没有集中在同一个文件，原先 4.719 秒的停顿本轮也未复现。下一步需要把 guest 任务调度和宿主执行进程调度与这些时间范围关联，现有证据还不能作因果归因。逐样本与逐步骤分析见 [stage-analysis.json](capture-v1/stage-analysis.json)，可用 [analyze-stages.py](capture-v1/analyze-stages.py) 从原始日志重算。

guest 结束且 69 个进程组独立确认清理后，又用**同一二进制**在 Starpub 原生运行四线程、各 6 秒，分别设置 CPU 0–3 与 CPU 0 亲和性。两轮各 60 个样本，最大完整采样分别为 0.478280 ms 和 0.525256 ms；两个进程组正常退出并独立确认为空，见 [原生审计](capture-native-v1/archive-audit.json)。原生使用外层共享 cgroup（实际 `cpu.max=3599999 100000`），与内部配额不同，这不能直接换算为 Docker 性能倍数或证明根因。内部运行、原生运行、输入哈希与清理证据分别保存，完整功能及性能验收仍未完成。
