## 完整候选用例 v3

[原始报告](v3/runtime/publish-v3.json) 为 **11 pass、1 fail、9 not_tested**，`subset_passed`、`full_acceptance` 和 `performance_acceptance` 均为 false。

- 已通过：daemon 接入、实际 guest 地址的引用计数和两轮释放复用、启动失败后的地址回滚、固定 IPv4 TCP/UDP 数据校验、停止重启及删除释放、默认和自定义 bridge 的端口冲突回滚、多端口原子回滚、正常关闭。

实际地址由 `network-probe addresses vec0` 读取。TCP 与 UDP 共用 `127.0.0.2` 时，guest 只增加一个 `10.0.2.17`；删掉 TCP 后保留，删掉 UDP 后释放，第二轮复用同一地址。占用外层端口导致容器启动失败时，guest 地址集合保持不变。此次 IPv6 是上游 Docker proxy 将 IPv6 主机监听转给 IPv4 bridge 容器，不包含 IPv6 容器网络的完整验收。

## 按大小定位 v2：IPv6 分片缺失

新实例 `publish-diag2` 复用相同内核、磁盘和跟踪 backend，逐个报文记录 connect/send/recv 阶段并校验全部返回数据。[实际结果](diagnostic-v2/report.json) 如下；MTU 保持 1500。

| 协议 | 报文大小（字节） | 结果 |
| --- | --- | --- |
| IPv4 TCP | 1、65536 | 全部正确返回 |
| IPv6 TCP | 1、65536 | 全部正确返回 |
| IPv4 UDP | 1、1200、1400、1452、1453、2000、8000、60000 | 全部正确返回 |
| IPv6 UDP | 1、1200、1400、1452 | 全部正确返回 |
| IPv6 UDP | 1453、2000、8000、60000 | 全部在 recv 超时 |

边界恰好是 `1500 - IPv6头40 - UDP头8 = 1452`。报头日志显示：1453 字节的 IPv6 UDP 被 backend 作为一个 1515 字节以太网帧发给 guest；guest 随后返回两个 `next=44`（IPv6 分片）帧，长度为 1510 和 75。固定版 libslirp 4.6.1 的 `ip6_input.c` 只分发 TCP、UDP 和 ICMPv6，分片进入默认释放路径。这把 1453 字节的回传失败定位到了缺少 IPv6 重组。

另一方向也有缺口：`ip6_output.c` 没有按 MTU 分片，日志直接出现 2062、8062、60062 字节的未分片出站以太网帧；对应大 UDP 请求没有成功回显。不能靠增加 MTU 或缩小测试报文把它计为修复。

[固定源码证据](libslirp-source-evidence/) 直接从校验 SHA256 的上游 4.6.1 源码包提取，包含 `ip6_input.c`、`ip6_output.c`、`udp6.c` 及版权文件。实际基线链接 Ubuntu `4.6.1-1ubuntu0.2`；该发行版唯一补丁修正 `socket.c` 的 TCP 紧急数据边界，没有修改上述 IPv6 路径。新的源码构建也必须保留该发行版修复。目录同时记录诊断结束后核对的安装库哈希，不把它冒充运行前已记录的库哈希。

本次 20 个报文检查为 16 成功、4 失败，仅用来定位故障，不替代完整发布用例。16 条 Docker/运行命令均正常退出，实例正常关闭，18 个记录的进程组独立复查为空，全部输入哈希保持一致。源码、逐条输出和完整的有限报头跟踪保存在 `diagnostic-v2/`。修复需要固定版本的 libslirp 补丁及新的实际 Docker 回归，目前仍未完成。

另在候选源码审查中发现控制接口 `list` 的固定输出缓冲区与增大的端口表上限不匹配，连续 `snprintf` 未检查截断后的位置，存在越界写风险。修复及大端口表检查尚在进行；该候选不能合入作为已可用实现。
