# CPU 时钟候选：真实 Docker 忙负载与动态限额

**五组实验正常完成，但整组均为 `indeterminate`，资源控制和性能仍未通过验收。** 开启高精度时钟的两组在动态更新阶段出现了较短的最长采样窗口；所有组的无限额参考负载均低于现有交付检查要求，不能仅凭这一变化宣布修复。

运行顺序为原内核、候选关闭、候选开启两次、候选再次关闭。每组保持 4 vCPU，分别执行无限额、`--cpus 1`、显式 `--cpu-period/--cpu-quota`、单核绑核、范围绑核、绑核加限额，以及同一运行中容器的 `docker update --cpus 2 → 0.5 → 2`。通过线程实际运行 CPU、亲和性、CPU 时钟、`cpu.stat` 和两次夹读的 `cpu.max` 判断，不能用配置写入成功替代执行效果。

| 条件 | 无限额进程 CPU 秒／墙钟秒 | 动态更新采样最长窗口 | 相邻采样起点最大间隔 | 其他无法判定项 |
| --- | ---: | ---: | ---: | --- |
| 原内核 | 3.835 | 798.098 ms | 898.549 ms | 绑核加半核限额 |
| 候选关闭 | 3.841 | 692.837 ms | 999.366 ms | 范围绑核 |

| 候选再次关闭 | 3.716 | 597.485 ms | 797.679 ms | 范围绑核、更新后两核恢复窗口 |

表中“其他”均不包含每组共同存在的无限额参考不足。采样窗口覆盖多个读取和调度等待；忙线程与观察线程在同一限额组，较长窗口中也包含正常配额等待，不能直接称为单次系统调用耗时。两次开启结果支持继续研究时钟粒度，但宿主负载仍未完全受控，原有计量还包含宿主调度等待，且尚无实际完成运算量与原生 Docker 命令耗时的对照。

原有 CFS 判定公式、时间窗口及阈值未改动。仅私有实验入口增加 `harddind_hr_sched_clock=0/1`，并给构建锁等待设置 90 秒上限。使用提交 `0c333f0` 的探针和检查器；随后新增的工作量计数不在本轮输入中。CPU shares 竞争仍为 `not_tested`，没有用单容器限额结果替代它。

共执行 335 个实际构建、CLI 与生命周期命令，退出码均为 0；五个测试运行器按规则返回 2，代表无法判定。2027 次采样及全部原始输出保留，五个 guest 正常关机，356 个受控进程组在结束后再次独立核对为空。所有冻结输入、基础磁盘和外部程序哈希未变。构建持有全局独占锁，guest 持有共享锁，五组串行，未运行 GPU 或其他 owner 性能实验。
