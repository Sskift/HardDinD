# GPU 追踪对照 v2：修复关机，GPU 仍间歇失败

本轮保留 v14 内核、CUDA 探针、镜像、设备、4 vCPU 和异步 GPU 等待。修复运行器的 Unix socket 路径，并把顺序改为日志、无追踪、两者、strace、strace、两者、无追踪、日志。

**关机缺陷已修复并在实际 guest 验证。** UML 从实例目录以 `uml_dir=uml/` 创建管理 socket；主代理通过 `/proc/self/fd/目录描述符/mconsole` 连接同一个文件。实例绝对 mconsole 路径仍是 109 字节，关机正常完成，guest 退出码 0，没有强制关机。3 项真实 Unix 数据报测试还覆盖长路径、短路径兼容、错误回复后的文件描述符和客户端 socket 清理。29 个记录进程组为空，输入哈希未变。

GPU 结果仍是失败，不能因管理流程完成而转为通过：

|---:|---|---:|---|
| 0 | 日志 | 2/4 | 后续上下文创建 CUDA 304 |
| 1 | 无追踪 | 0/4 | 上下文创建 CUDA 304 |
| 2 | 日志 + strace | 4/4 | 通过 |
| 3 | strace | 4/4 | 通过 |
| 4 | strace | 4/4 | 通过 |

| 6 | 无追踪 | 1/4 | 后续上下文创建 CUDA 999 |
| 7 | 日志 | 1/4 | 退出码 139 |

每个已校验 GPU 均完成上传、PTX 计算、下载及全部 1,048,576 个元素的精确比较。原生前后对照各四卡完整通过。第 0 和第 7 轮日志均捕捉到 class `0xc56f` 的分配请求返回 EIO；第 7 轮随后发生异常退出，尚无崩溃栈，不能仅凭退出码命名具体代码缺陷。

与 v1 合看，带 strace 的已测运行都完成，无追踪和仅日志的运行有成功也有失败。它提示执行时序或追踪相关路径值得检查，**不证明 strace 是修复，也不证明具体竞态原因**。失败可以出现在同一进程的后续 GPU，不能局限为首次初始化失败。

`owner-status.json` 的退出码 0 仅表示八组诊断、前后原生对照和正常清理全部完成；`full_acceptance` 和 `performance_acceptance` 均为 false。本轮没有同条件 GPU 性能比较。失败没有重跑覆盖，完整日志和冻结运行器在此保留。

执行 `python3 recheck.py` 复核原始四卡/部分结果、失败码、哈希和正常关机。后续 v3 使用同一内核关闭异步等待，单独检验异步完成路径的影响。
