# GPU 映射 v7：恢复控制语义，定位 Docker 设备号问题

owner 在 v6 源码上仅恢复固定命令 `0xd04` / `0x1f0` 的标志和长度校验例外，让真实驱动决定错误顺序；客体预先访问的仍是有界规范结构大小。构建前后跟踪源码一致，14 个目标文件经无模糊补丁重放后逐字节一致。

实际结果：

- 系统控制：原生前后对照和内部客体 **31/31 一致**，修复了 v6 的全部七个差异。
- 固定分配：原生前后对照和内部客体 **74/74 一致**。
- 内部 Docker CUDA：**失败**，`cuInit` 返回 100。原生前后各完成四卡计算、传输和结果校验，但内部没有开始计算。

失败原因由原始系统调用轨迹确认：诊断脚本把新内核的兼容别名挂到容器 `/dev/nvidiactl`，其设备号为 `252:255`。NVIDIA 库要求标准设备号 `195:255`，删除并重建设备后，打开操作被内部容器的设备规则拒绝（`EPERM`）。UVM 节点存在不代表 CUDA 可用。

内核 SHA-256 为 `a320dabbae15422ccfcd8dd482a3ee92899dea9162cce5d722dc4702364f8e16`；补丁为 `f7aad4768e56cc82933b6d7b9bf9074b30266f01ade17b994e0e4c96b807c891`。基线为相邻 `gpu-mapping-v4/baseline/`，旧 v6 回归及失败 v5 准备过程保留在相邻归档中。内核二进制、磁盘和完整上游树未收录。

三个实验均正常结束。独立审计确认本轮保留下来的 **15 个构建/运行进程组为空**。旧 CUDA 脚本尚未保留所有辅助命令的进程组明细，因此不把该数字声称为所有辅助命令的独立覆盖；v8 起的新脚本补充了完整命令账本。

后续 [v8](../gpu-mapping-v8/README.md) 仅改变设备节点选择，使用同一内核继续诊断；[v9](../gpu-mapping-v9/README.md) 使用相同新脚本验证旧后端回退。联合离线复核命令：

```sh
python3 results/starpub-2026-10-15-candidate-review/gpu-mapping-v7/recheck.py
```

复核包括冻结源码/补丁、原始控制结果、CUDA 原生前后计算、设备号故障、标准节点和旧后端回退、输入哈希及清理记录。它不会运行 GPU，也不会把内部 CUDA 失败改判为通过。候选映射补丁尚未并入默认内核路径。
