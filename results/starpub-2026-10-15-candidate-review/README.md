# 未合入候选的审查与失败证据

这轮在 Starpub 恢复连接后检查并行任务，发现 CPU shares 校验器的缺证据误判，以及浮点、GPU 过滤器模型的挂起。下列源码是发现问题时的快照，**不是主线实现，也不是新的功能或性能通过记录**。修复任务仍在 Starpub 的独立目录继续。

## CPU shares：缺失关键证据仍返回通过

`cpu-shares/` 保存候选脚本、测试夹具和在 Starpub 执行的反例。保持候选自带的正常合成负载不变，分别删除下列数据，整体判定仍为 `pass`：

- 全部命令记录和生产者提供的必需命令列表。
- 全部运行前、后的输入哈希。
- 所有阶段快照中的有效 cpuset。
- 容器清理后的剩余容器清单字段。

`counterexamples.json` 和 `reproduce.stdout` 记录 1 个正常夹具、4 个缺证据反例，`reproduce-status.json` 的退出码 0 表示**成功复现误判**。没有运行实际 Docker shares 竞争，也没有把这些合成结果算成功能通过。在 Linux 上可用以下命令复现冻结版本：

```sh
timeout 20 python3 cpu-shares/reproduce.py
```

还发现一个尚未运行验证的时间边界错误：脚本只在更新权重后抓取快照，校验器却把这份快照减去固定 0.6 秒作为上一阶段的结束时间。更新及快照耗时超过该值时，上一阶段可能含有下一阶段的执行量。修复须记录更新前后的边界，证明两个容器计量区间的实际重叠，并严格拒绝缺失证据。

## 浮点状态缓存：引用与锁顺序仍有缺陷

`fp-lifetime-v2/` 保存候选补丁、模型和具体审查意见。补丁 SHA256 以 `bdbde34b70cf` 开头。它为 runner 的 owner 增加了任务引用，但仍存在：

- 多条空 owner 路径无条件调用 `put_task_struct(NULL)`。固定 Linux 7.2.10 的该函数会访问 `t->usage`；候选模型的 `task_put` 和 `slot_release` 却允许 NULL，未忠实模拟这个前提。
- `uml_fp_exit` 先取得 descriptor 锁，再取得 handoff 锁；其他相关路径顺序相反，存在 ABBA 死锁风险。
- 更改后的函数签名与调用点不匹配，以及 `WARN_ON_ONCE` 的参数数量错误。

这些是**对应源码快照的静态发现**，没有冒充实际 guest 内核崩溃。此前的 [ASAN 任务释放反例](../starpub-2026-10-15-fp-owner-lifetime/README.md) 仍单独保留。

远端 `/tmp/fpm_asan` 的模型运行另已等待超过 2500 秒，主线程停在 futex 等待，其他线程在休眠。`hung-model.json` 保存当时的进程、线程状态和二进制哈希；内核栈读取被外层权限拒绝。主代理只向核对过身份的测试进程发送 SIGTERM，并将挂起作为失败处理。没有把等待状态直接归因为上述内核锁顺序，也没有独立证明该二进制与保存的补丁完全对应。

## GPU 过滤器模型：阻塞用例未受超时保护

`gpu-filter/` 保存实际过滤器源码、测试生成器和模型。模型的一组子进程阻塞，父进程等待它退出；`process.json` 记录父进程的 `do_wait` 和子进程的 `unix_stream_data_wait`。主代理核对路径后终止这两个测试进程，交回补充外部超时、完整进程组回收和正确的信号帧测试。

这份记录证明测试没有正常结束，不能据此认定候选 GPU 功能已经通过，也不能把模型挂起等同于内部 CUDA 的失败原因。对应修复还需要冻结源码、构建和实际内部 Docker 验证。

## 证据边界

后续 [GPU 过滤器 v3 独立验证](gpu-filter-v3/README.md) 已完成四种配置的 8 次模型执行，并独立确认全部进程组退出。该记录同时保留完整候选内核的构建失败，未把模型通过算成内部 GPU 验收；上述原始挂起证据继续保留。

`source-integrity.json` 固定归档的 16 个文件。`cleanup-audit.json` 是终止后的独立检查：两个测试进程组均无存活或僵尸成员，三个目标 PID 均已不存在。归档只涉及候选和模型；主线内核、现有实例以及 `/root/udock` 未因这些审查被替换。
