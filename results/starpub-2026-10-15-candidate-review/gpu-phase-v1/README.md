# GPU 分阶段与正反卡序诊断

固定修复内核、驱动库和设备，异步等待开启，无日志注入或 strace。每个进程依次使用四张 GPU，每张卡在同一上下文内执行 8 次计算，前两次为预热、后六次计时；三阶段分别按正序、反序、反序、正序运行。12 个进程共 **384 组计算及逐元素校验通过**，16 条命令成功，19 个记录的进程组为空，正常关机且输入哈希未变。

每次迭代改变输入，并在计时前将输出写成哨兵值，防止上一轮结果被误当成本轮计算。用整数 `CLOCK_MONOTONIC` 纳秒分别记录两次 HtoD、launch 调用、同步和 DtoH。这里是 CPU 观察到的 API 调用时间：同步中可能包含此前异步 GPU 工作及调度等待，**不是 CUDA event 测得的纯 GPU 时间**。初始化、JIT、分配、输入填充和输出预写在计时之外。

正序的部分中位耗时如下，单位 ms；同一单元包含两次独立进程中各六个计时样本。原生前后不合并，各阶段的中位数之和也不等于总耗时中位数。

| GPU / 阶段 | 原生前 | Docker | 原生后 |
| --- | ---: | ---: | ---: |
| 0 / 总计 | 3.801 | 5.001 | 5.030 |
| 0 / 同步 | 1.033 | 1.719 | 1.353 |
| 1 / 总计 | 3.731 | 5.584 | 4.196 |
| 1 / 同步 | 0.771 | 1.905 | 1.341 |
| 2 / 总计 | 3.803 | 3.945 | 4.201 |
| 3 / 总计 | 2.910 | 3.199 | 3.488 |

当前可排查同步等待和 launch 提交路径，但原生对照也有变化，不能把所有差值都归因于 UML。反序数据和所有原始样本完整保留在 `owner-status.json` 及命令输出中，未挑选有利顺序。没有性能通过结论。

**与上一轮的关键区别：**本探针预写输出哨兵，使 4 MiB 输出内存在计时前被触碰；`gpu-plain-perf-v3` 的原探针分配后未写输出缓冲区，首次 DtoH 会首次写入它。加上同一上下文内重复，本轮与原探针有两个变化，不能直接把 GPU 0 从约 18.6 ms 降至约 5 ms 称为优化收益。后续用同一个程序可选冷输出/预写输出，配合正反卡序，验证首次内存触碰的贡献。

这只是顺序四卡小负载诊断，不含 GPU event、唯一设备身份记录、并发生命周期或完整应用验收。`recheck.py` 重新核对原始行、阶段加和、分组中位数及清理记录。
