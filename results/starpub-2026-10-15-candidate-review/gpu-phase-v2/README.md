# 首次回传的输出内存对照

同一程序通过参数选择 `cold` 或 `prefault`：冷模式在第一张卡的第零次迭代前不触碰刚分配的 4 MiB 输出缓冲区；预写模式在计时前写入哨兵。两者其余 API、计算和校验完全相同，后续迭代都改变输入并预写输出。每阶段依次执行正序预写、正序冷、反序冷、反序预写，保留原生前、内部 Docker、原生后三组独立数据。

异步等待开启，无追踪，全部 **384 组计算校验通过**；16 条命令成功，19 个记录的进程组为空，正常关机且输入哈希未变。

第一张卡第一次 DtoH 的实际耗时如下，单位 ms。每个格子是一条观察值，不是大量重复的中位数。

| 卡序 / 输出模式 | 第一张卡 | 原生前 | Docker | 原生后 |
| --- | ---: | ---: | ---: | ---: |
| 正序 / 预写 | 0 | 0.983 | 0.956 | 1.228 |
| 正序 / 冷 | 0 | 4.231 | 16.674 | 4.394 |
| 反序 / 冷 | 3 | 4.206 | 13.366 | 3.679 |
| 反序 / 预写 | 3 | 1.046 | 1.121 | 1.008 |

这次对照把明显的额外成本缩小到首次 DtoH 写入未触碰输出内存的路径；反转卡序后，成本转移到 GPU 3，不能继续只归因于 GPU 0。它还没有直接测量缺页数量、缺页处理时间或纯 GPU event 时间，不能进一步声称全部差距已由缺页解释。原生前后有变化，每种条件每阶段仅一个独立进程，不能建立完整性能结论。

**预写不是已经完成的性能优化。** 它把首次内存触碰移动到测量区间外，应用仍需支付这个成本。后续纯 CPU 首写及缺页计数对照用于继续定位，真正的优化须减少该路径成本并重新测量完整工作负载。原始冷路径结果继续保留，不用预写结果替代验收。

每张卡其余七次迭代、两次 HtoD、launch、同步和总耗时均保留；`recheck.py` 从原始行复算每种条件的首轮值及后六轮中位数，并验证实际命令参数与标签一致。
