# GPU 追踪对照 v1：间歇失败和关机路径缺陷

固定 v14 内核 `9306f4e6…`、磁盘、镜像、CUDA 探针和设备集合，在一个新实例中运行 8 个新容器。只改变日志注入与 strace，所有容器显式删除。运行顺序与结果：

| 顺序 | 运行方式 | 四卡计算和逐元素校验 |
|---:|---|---|
| 0 | 无注入、无 strace | 通过 |
| 1 | 仅 LD_PRELOAD 日志 | 通过 |
| 2 | 仅 strace | 通过 |
| 3 | 日志和 strace | 通过 |
| 4 | 日志和 strace | 通过 |
| 5 | 仅 strace | 通过 |
| 6 | 仅 LD_PRELOAD 日志 | 创建上下文失败，CUDA 304 |
| 7 | 无注入、无 strace | 创建上下文失败，CUDA 304 |

每个成功容器均对每张卡校验 1,048,576 个元素，失败容器没有计算结果。前原生对照四卡成功。**这反驳了“无追踪一定失败”或“有日志一定成功”的解释，未确定根因，更不能认为普通运行稳定。** 所有时间都含不同诊断条件，本轮不作性能对比。

第 6 轮保留了失败的 ioctl 日志：唯一负返回发生在 `NV_ESC_RM_ALLOC`（`0xc030462b`），分配 class `0xc56f` 时返回 `-1/EIO`，输入输出的 48 字节头未改变。此前成功的分配仍在同一份日志中。它将定位范围缩到通道分配路径；尚未区分桥接层、映射或原生驱动返回，不能把 EIO 直接解释为已证明的根因。

本轮整体退出码为 **1**：结束时 mconsole 的绝对路径为 109 字节，Python Unix socket 操作报 `AF_UNIX path too long`，运行器强制终止 guest，后原生对照因此没有运行。全部 27 个记录的进程组最终为空，输入未变；**清理完毕不等于正常关机通过**。原始失败和状态不改写，修复运行器后另建 v2 验证。

`archive-sha256.json` 校验原始日志；四份 strace、每个容器的标准输出/错误、命令和清理状态均保留。执行 `python3 recheck.py` 可从原始记录重算上述事实。内核、CUDA 探针和日志器对应 [v14 冻结源码](../gpu-mapping-v14/README.md)，本轮没有改动这些输入。
