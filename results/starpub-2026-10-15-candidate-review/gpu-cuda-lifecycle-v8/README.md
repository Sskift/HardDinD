# GPU 锁顺序候选：超时消失，多 context 仍失败

本轮使用与 [v7 锁循环诊断](../gpu-cuda-lifecycle-v7/README.md) 相同的冻结 CUDA 程序，在 Starpub 执行原生前、内部 Docker、原生后对照。**内部程序约 24 秒走完整个流程并返回失败，没有再次触发 180 秒超时；整体 GPU 验收仍失败。**

| 范围 | 实际结果 |
| --- | --- |
| 内部四卡逐卡计算 | 每卡 8 轮，上传、计算、下载和逐元素校验成功；每卡 24 次分配、24 次释放 |
| 同一进程的四个线程 | 三个线程创建 context 返回 304，未计算；GPU 3 的线程完成 4 轮 |
| 四个独立 exec 子进程 | 全部完成 context 创建及各 2 轮计算、双向传输和结果校验 |
| 12 个有向卡间组合 | 第一个 context 成功，第二个均返回 304；没有进入 peer enable 或传输 |
| 原生前后 | CUDA 操作和 12 个卡间传输完成，但严格并发覆盖检查均失败 |

四个内部子进程的记录工作区间有 62.717 ms 公共交集。这不是硬件 kernel 同时执行的证明，短周期测试也不能代替长期并发验收。原生前的子进程区间交集为 −6.055 ms，原生后的线程交集为 −2.465 ms，因此三个阶段的 `phase_pass` 均保留为 false。旧探针起跑门和短负载覆盖问题继续单独修复，没有放宽判定。

## 候选改动与构建

`0029-um-gpu-usercopy-lock-order.patch` 让 ioctl 的输入快照使用独立 `kmalloc` 缓冲区。可能缺页的用户访问和描述符引用获取发生在 `gpu_lock` 外；锁内只将私有缓冲区复制到共享影子页、同步映射、执行 worker 命令，再复制回私有缓冲区。输出复制在解锁后执行。事件分配路径的用户复制也移到锁外，描述符引用仍由调用方统一释放。

这针对 v7 实际栈中的 `gpu_lock → mmap_lock` / `mmap_lock → gpu_lock` 循环。新增私有分配有明确 `ENOMEM` 路径，尚未宣称与旧版内存压力行为一致。一次完整运行不代表所有锁循环或长期并发问题已解决；304 是否为本次改动引入，仍需旧、新内核的最小 context 对照。

主代理在独立源码树构建，保持原内核 `.config` 字节不变，追踪的 33 个源码文件在构建前后相同。两段 150 秒构建达到时间上限并清理，第三段完成链接；这些超时原样保留在 `author-evidence/build-status.json`，没有算作正常构建退出。

## 清理与复核

内部保持 4 vCPU 和异步 GPU 等待。17 条命令中，CUDA 程序及三个阶段校验按上述原因返回 1，其余返回 0；没有运行时命令超时。容器已删除，guest 正常退出，独立检查的 20 个进程组均无存活或僵尸成员，输入、源码和驱动库未变。

运行 `python3 recheck.py` 可重新核对归档哈希、33 文件源码绑定、补丁重放、构建记录、原始 CUDA 返回和三个阶段的失败判定。这个脚本验证证据一致性，不会运行 GPU，也不把失败转为功能通过。测试仍使用显式设备参数；标准 `--gpus` 接入、完整 GPU ABI、长时间生命周期和性能均未验收。
