# GPU 同步等待对照 v3

与 v2 相同的 v14 内核、磁盘、探针、镜像、设备、4 vCPU、运行器修复和八组顺序，**只关闭 `gpu_async_wait`**。8 个内部容器全部完成四卡计算、上传/下载和逐元素校验，原生前后各四卡通过；实例正常关机、29 个记录进程组为空、输入未变。

v2 开启异步等待时同一顺序为 4/8 完整成功，另有 CUDA 304、999 和退出码 139。v3 的结果支持继续检查异步交接，仍不能凭一个开关对照唯一确定根因，或认为关闭异步等待即可交付：同步等待会占住对应的 guest 执行路径，不满足最终并发操控与性能目标。本轮没有性能验收结论。

主代理从冻结的 `stub_signal_interrupt` 找到具体交接窗口：同步请求的 worker 发布 `FUTEX_IN_KERN` 后才读取共享 `gpu_async`。此时调用者可能已设置下一条异步请求的标志，导致旧请求发出新请求的提前完成通知，调用者读取尚未更新的默认 EIO。它能解释 v1/v2 的部分现象，但这份记录只是同内核开关对照；修复后的实际异步运行、独立协议复核和回归另行保存。

所有成功容器各校验 4 × 1,048,576 个元素，完整原始记录、命令及输入哈希见本目录。`python3 recheck.py` 重算原始结果与清理状态；不把控制实验成功改写成完整 GPU 验收。
