# CPU 采样停顿：四组真实对照

Starpub 在 2026-10-15 完成四组内部 Docker 诊断。每组 60 次采样、每次五个操作阶段，均完整结束；外层采样覆盖全部 300 个阶段，39 个记录进程组独立复查为空，guest 正常关机。此前的 CPU shares 间隙没有被改判通过，本轮也没有性能验收结论。

| 观察进程位置 | 单次采样中位数 | 单次采样最长 | 相邻采样起点最大间隔 |
|---|---:|---:|---:|
| 0.5 CPU 限额组，无忙线程 | 0.310 ms | 479.205 ms | 524.180 ms |
| 无限额组，无忙线程 | 0.319 ms | 2.984 ms | 106.139 ms |
| 独立无限额组，旁边有 0.5 CPU 限额的四线程负载 | 0.265 ms | 2.146 ms | 192.222 ms |
| 与四线程负载同处 0.5 CPU 限额组 | 1.565 ms | 497.781 ms | 484.253 ms |

没有忙线程的限额组中，第 20 次采样读取 `cpu.max` 的阶段耗时 478.995 ms，guest 线程 CPU 时钟增加 200 ms。它提供了进一步检查计量和调度路径的具体位置，尚不能据此确认内核缺陷，也不能断言外层没有调度等待。另一组同限额观察进程的长停顿还需区分正常限额等待与额外开销。

外层采样器开销显著：四组分别消耗 5.80、6.47、6.99、18.23 CPU 秒，对应 11.15、8.36、8.75、22.39 秒运行时间。采样器和实验继承同一组四个宿主 CPU；这些数据受观察开销影响，不能当作无干扰性能基准。主机与 guest 时钟对齐的不确定区间约 13–24 ms，也不支持对微秒级阶段进行精确归因。缺失的 PID 世代和不可用的等待计数必须继续保留为未知。

主代理先运行 28 项实际夹具检查，无跳过，再执行串行实验。两个有忙线程的配置各自启动独立负载，并确认负载在观察前后持续运行。结束后在 Starpub 从原始 host samples 和 witness 输出重算四份关联结果，均与原结果完全一致；`owner-analysis.json` 保存重算和延迟统计，`owner-analyze.py` 保存计算方法。

`archive-sha256.json` 固定探针、分析器、运行器、原始输出、主机采样和关联结果。大 JSON/JSONL 以 gzip 保存，不删减原始记录。运行本目录 `recheck.py` 可复核归档、原始采样计数及时间统计、输入身份和清理记录。当前工作是定位并修复差异，不能用迁出限额组的诊断配置替代生产容器资源限制。
