# 默认关闭的 UML rseq 候选

新增 `kernel/experiments/0029-um-opt-in-rseq.patch`，让 x86-64 UML 可选择使用内核现有 rseq 实现。CPU 编号由 guest 调度器维护；补丁接入信号帧建立前的 rseq 修正、指令指针设置和可选调试入口。已有 `interrupt_end()` → `resume_user_mode_work()` 负责调度后的更新。未把宿主 CPU 编号传给容器，未改变 seccomp、ptrace 或资源控制入口。

`CONFIG_UML_X86_RSEQ` 默认关闭，补丁未加入默认构建序列。当前仅作为实验候选保留，**尚未通过整体功能或性能验收**。

## 构建绑定

从固定 Linux 7.2.10 压缩包重新解压，按基线清单重放全部 23 个补丁，再应用本候选。基线修改文件的 SHA256 全部匹配，完整编译、链接和 stub 重定位检查通过。保留原有内核配置，仅新增 `UML_X86_RSEQ`、`HAVE_RSEQ`、`RSEQ` 和它选择的 `SCHED_MM_CID`。

- 候选内核：`61de2cffc70f9c784e55e63beada243135eac0c500ce4529ef8ad2de752ffabc`
- 候选补丁：`9f28b53cc3469cb7ffe4e7e6f093efb6f7a5981add13d8fe06c61274e91fe9df`
- 候选配置：`48eda2ee21fe07dac9f868a447f1c040df328589ac900bff13b19a88a61d64d3`

实际构建源码和二进制在 `/root/harddind-rebuild/rseq-owner-v1`。`build.tar.gz` 包含构建脚本、日志、完整基线补丁、配置、候选修改文件及固定版本的 rseq 自测源码。可按该脚本重建；它使用独立输出目录及全局构建锁。构建脚本曾请求 `DEBUG_RSEQ`，但基线未开启其 `DEBUG_KERNEL` 依赖，解析后该选项未生效；本轮没有调试模式通过结论。

## 查询路径实测

使用与 [基线查询诊断](../clock-query-v1/README.md) **逐字相同的静态二进制**，分别执行外层前后参照、内部 1/4 线程和 `--cpuset-cpus=2,3`。共 285 条线程记录通过返回值、时间单调性和 CPU 集合检查。guest 始终为 4 vCPU、4 GiB，未运行 GPU；所有实验串行进行。

| 单线程查询，中位数 ns/循环 | 基线内部 | rseq 候选内部 |
| --- | ---: | ---: |
| libc `sched_getcpu()` | 4,334.28 | 3.76 |
| libc `clock_gettime()` | 4,715.65 | 4,329.41 |
| 两者连续调用 | 8,783.55 | 4,280.77 |

候选内部 glibc 的 rseq 注册大小由 0 变为 32。4 线程和受限 cpuset 下的 CPU 查询中位数分别为 5.84、6.15 ns/循环。该查询已消除主要的系统调用成本，但时钟仍走原来的系统调用路径，多线程时钟耗时有明显波动。短时分解数据不能证明整体加速或与原生性能一致，原有 CPU 工作量程序也未因本轮而改变。

## 实际语义检查与保留的失败

自测均在真实内部 Docker 容器运行，外层前后使用同一批静态二进制。`src/rseq_lifecycle_probe.c` 检查 4 线程反复切换 CPU、rseq 缓存与直接 `getcpu` 的一致性、fork 后继承、exec 后注册，以及父进程后续状态。其余使用固定 Linux 源码中的真实 rseq 注册错误和关键区操作自测。

- v1 原始报告为 10 pass / 26 fail。上游参数测试要求自行注册，但 glibc 已注册导致入口失败；外层 `basic_test` 还因节点编号字段不可用触发断言。全部失败保留。
- v2 按上游运行脚本设置 `GLIBC_TUNABLES=glibc.pthread.rseq=0`，让上游程序自行注册；生命周期程序继续验证 glibc 的自动注册。普通关键区递增、链表、缓冲区、内存复制、非法注册参数及生命周期通过。外层前后 `basic_test` 的节点字段断言仍失败，未算通过。
- v2 原始报告写了 34 pass / 2 fail，但主代理复核发现信号/让出测试的注入点 7 未被 x86 操作使用，信号数实际为 0。**按预期事件修正为 26 pass / 2 fail / 8 not_tested**，原始报告保留，不能引用其名义通过数作为验收。
- v3 改用有效的 C 注入点 9，并增加 16 线程关键区延时来触发调度中止。外层前后、内部全部 CPU 和受限 cpuset 的 12 次定向运行通过；每组信号测试实际交付至少 4,000 个信号，预占实验观察到的 rseq 中止数分别为 56、72、42、52。检查要求实际事件出现，不能只看退出码。

这些运行都正常关机，175 个运行期命令的原始输出和 187 个空进程组记录已归档。源程序编译日志和构建过程另存于 `build.tar.gz`。没有采用新的性能容差。
