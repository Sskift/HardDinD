# 同一 GPU 映射内核 v8 诊断：标准节点生效，缺少两类 ioctl

与 v7 使用**同一内核** `a320dabbae15422ccfcd8dd482a3ee92899dea9162cce5d722dc4702364f8e16`。本次修改 `scripts/run-gpu-cuda.py`：优先选择客体标准 `/dev/nvidiactl`、四个卡节点和 `/dev/nvidia-uvm`，只有明确缺失时才回退到旧兼容别名；其他错误不回退。编译纳入全局锁，并保存每条辅助命令的退出状态及进程组清理记录。

真实 Docker 容器已成功打开正确设备号的控制/卡节点和 UVM，设备替换后的 `EPERM` 问题消失。CUDA 初始化仍失败，尚未完成内部计算。轨迹中恰好有以下两类实际负返回，每类出现四次：

| 操作 | 实际返回 |
| --- | --- |
| ioctl `0xc23046d7` | `-1 / EOPNOTSUPP` |
| RM_CONTROL `0x216`，参数长度 128 | `-1 / EOPNOTSUPP` |

UVM 初始化/反初始化及已有设备信息查询已执行。日志中成功调用后保留的旧 `errno` 不算失败；上述两类均按 `rc=-1` 确认。下一步需要从固定 NVIDIA 550.120 源码证明这两类请求的数据布局和指针/描述符语义，再扩展转发，不能盲目放行未知 ioctl。

原生前后各完成四张卡的实际计算、传输和结果校验。内部 `cuInit` 返回 100，因此 `internal_cuda_verified=false`。`diagnostic_complete=true` 仅表示诊断流程完整，不能视为 CUDA 通过。客体正常停止，输入和驱动库哈希未变，**全部 14 条命令加客体/网络共 16 个进程组独立核实为空**。

`build-lock-deadlock.json` 记录本次启动前排队发现的构建脚本嵌套锁故障：外层持锁，内层重新打开同一锁后等待外层。owner 只终止经身份核验的锁等待进程，使构建调用退回失败，再交回修复。没有把排队耗时或本次带跟踪的 CUDA 运行用作性能数据。

原始脚本、探针、日志、状态和哈希均保留；内核和镜像内容由 v7 及既有固定版本构建记录关联，二进制未重复归档。与 v7/v9 的联合复核见 [v7 说明](../gpu-mapping-v7/README.md)。完整 GPU、`docker --gpus` 集成、多进程/线程生命周期及性能目标仍未达标。
