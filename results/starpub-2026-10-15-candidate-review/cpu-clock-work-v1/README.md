# CPU 时钟候选：工作量与内部 Docker 对照

**实际完成工作量已在内部验证；五组 CPU 限额整体验证仍为 `indeterminate`，时钟候选没有稳定加速，未合入。** 本轮补齐此前工作量探针仅在原生执行的缺口，不作为整体 Docker 性能通过。

同一静态二进制在同机原生前后运行，并在原内核、候选关闭、开启两次、再次关闭五个独立 guest 中执行完整 CPU 限额检查。每组保持四个 vCPU，覆盖无限额、`--cpus`、显式 quota/period、单核及范围 cpuset、cpuset 加 quota，以及同一容器的 `docker update --cpus 2 → 0.5 → 2`。所有 35 个容器负载和两个原生负载的运算块数与最终结果一致。

| 条件 | 无限额进程 CPU 秒／墙钟秒 | 实际运算块／秒 | 动态更新最长采样窗口 |
| --- | ---: | ---: | ---: |
| 原生前 | — | 1,894,567 | — |
| 原内核 | 3.848 | 55,939 | 533.0 ms |
| 候选关闭 | 3.887 | 68,766 | 700.3 ms |
| 候选开启，第一次 | 3.849 | 43,694 | 104.3 ms |
| 候选开启，第二次 | 3.865 | 92,213 | 294.1 ms |
| 候选再次关闭 | 3.910 | 78,806 | 300.7 ms |
| 原生后 | — | 1,751,843 | — |

每块为 1024 次依赖整数运算，随后查询当前 CPU，并在下一轮读取单调时钟。它是带高频系统接口查询的特定负载，不能把表中差距推广为所有纯计算，也不能通过删去查询来宣称后端优化。内部工作量约为这两个原生参照的 2.3%–5.3%，说明接近四核的 guest CPU 时间统计并不代表交付了相应的原生计算量。高精度时钟开启两次相差明显；本轮不能确认稳定收益或证明限额计量正确。宿主其他任务负载仍未完全受控，原生没有匹配的可写限额 cgroup 或 Docker daemon，因此限额条件下的原生 Docker 性能仍未测。

共记录 335 个实际构建、Docker CLI 和生命周期命令，1934 次采样，五个 guest 正常关机；358 个受控进程组在完成后再次独立复查为空。冻结源码、内核、基础磁盘和外部程序哈希未变，原生与全部内部探针二进制的 SHA256 一致。运行器按已有判定返回 2；没有改变 CPU 限额的公式、窗口或性能标准。CPU shares 竞争仍为 `not_tested`。

本轮使用 `11138e6` 的冻结源码，执行时使用的旧校验器也保留。离线复核同时使用修正周期别名边界的 `period-checked-cpu.py` 再验算原始工作记录，全部通过；不修改原始数据。内核与源码绑定沿用 [CPU 时钟源复核](../cpu-clock-v1/README.md)，二进制仅记录远端哈希，原始输出压缩保留。
