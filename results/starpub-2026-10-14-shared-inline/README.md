# 文件锁分派优化实验

当前未完成，下面的完整 ABBA 对照观察到局部耗时下降，不能声明接近原生或生产可用。`shared-inline-v1` 原生 21 项通过、Docker 19 项通过及 2 项 POSIX 范围锁失败；**关机还出现 45 秒超时，最终强制结束 guest**。失败证据完整保留，未纳入有效性能对照。

## 改动

`virtiofs/patches/0004-inline-flock.patch` 将 virtqueue 锁的作用域缩短到取出描述符。原来的 while-let 条件临时值会持有锁直到循环体结束，工作线程完成回复也需要同一把锁。

可选 `--inline-flock` 在事件线程中尝试一次非阻塞宿主 flock；数据表或文件内部锁忙时返回异步路径，真正发生文件锁竞争的阻塞请求继续进入可取消的等待队列。普通 I/O 仍使用 4 个工作线程。新增 Rust 检查实际持有内部写锁以及独立宿主 flock，验证不会把内部锁忙误报为 guest 文件锁冲突，也不会绕过外层锁。固定构建的 5 项补丁检查通过。

运行器通过 `--share-inline-flock` 启用，默认关闭。`--virtiofsd PATH` 可以选择不可变的服务二进制，路径和 SHA256 都记录到实例输入，便于对照不同版本。新服务 SHA256 为 `82743fb83d42c5e63633b607f26fb84a2ed2b8a20e7ca2b1375272f5d54d1790`；旧服务为 `bd689aefb17d8a454f4f587c47d342f0b5c5686f96cd07cbee69cbb7b92a8a1b`。两者都使用固定 virtiofsd 1.13.2 和 Cargo.lock。

## 首轮失败

计数确认 12036 次请求直接完成，9 次进入等待队列，内部锁忙回退为 0；取消队列的 2 次中断均被处理，退出日志中 remaining=0。19 项通过的检查包括双向锁排他、dup/fork、正常关闭、强杀与信号取消、6 个等待者及只读 bind mount。

guest 已输出 `HARDDIND_RUNTIME_STOPPED`，但没有在 45 秒内退出。记录中的 guest 退出码为 -9、forced_shutdown=true，文件服务退出码为 1；最终进程组没有残留。由于停止失败，没有执行最后一组原生样本，`benchmark_complete=false`。不能用本轮约 0.279 秒的 Docker 中位耗时宣称比前轮更快。

目前未证明超时由这次分派修改导致，也未证明与它无关。运行器现在在关机超过 15 秒时请求 guest SysRq 任务/CPU 栈，并记录本实例宿主进程组的 stat、wchan 和 syscall；保持原有 45 秒截止时间，读取失败也保存错误。后续复现必须检查这些证据，不能靠增加超时或重测通过覆盖首轮失败。

## 第二轮完整复测

`shared-inline-v2` 使用相同内核、磁盘、探针和文件服务，仅运行器增加前述关机诊断。原生 21 项通过、Docker 19 项通过及 2 项 POSIX 范围锁失败；62 个探针进程组均正常清理，guest、网络和文件服务正常退出，没有强制关闭，也没有触发延迟关机诊断。两轮的全部原始记录均保留，首轮超时原因仍未解决。

本轮 12 个计时样本完整，输入哈希未改变，未开启请求计时插桩。1000 次加锁/解锁的中位数为原生 0.0015968895 秒、Docker 0.155337344 秒，约 97.3 倍耗时。12036 次请求直接完成、9 次进入队列、内部锁忙回退为 0。该次复测没有交错旧版本对照，而且宿主负载变化，不能据此归因提速或声明性能达标。

## 对照入口

`scripts/compare-shared-locks.py` 按旧、新、新、旧顺序串行运行，无插桩，每阶段都有同机原生前置与后置各 3 个样本、Docker 6 个样本，使用相同内核、磁盘、探针和 CPU 0–3。此时 `run-shared-locks.py --benchmark-only` 的功能检查明确保持 not_tested，不把计时阶段算成功能验收。任何阶段输入变化、退出失败、缺样本或缺少真实 inline 路径计数都会使比较失败。

```sh
python3 scripts/compare-shared-locks.py /root/harddind-rebuild \
  --kernel /root/harddind-rebuild/virtiofs-interrupt-kernel-v1 \
  --disk /root/harddind-rebuild/runtime-shares-v1.ext4 \
  --baseline /root/harddind-rebuild/virtiofsd-profile-v1 \
  --candidate /root/harddind-rebuild/virtiofsd-inline-v1 \
  --name new-inline-abba
```

`inline-abba-v1` 已完成全部四阶段，旧、新、新、旧各有 12 个完整样本，每阶段均正常关闭，未使用强制回收。输入哈希未改变，功能检查保持 not_tested。旧版和新版各 12 个 Docker 样本的汇总中位数为 0.190715136 和 0.126125056 秒，新版/旧版为 0.6613，本轮观察到约 33.9% 的耗时下降。新版两个阶段均有 12000 次直接完成计数。

| 阶段 / 服务 | 原生秒数中位数 | Docker 秒数中位数 | Docker / 原生 |
|---|---:|---:|---:|
| 0 / baseline | 0.001810430 | 0.200205184 | 110.58 |
| 1 / candidate | 0.001468301 | 0.119482240 | 81.37 |
| 2 / candidate | 0.001650307 | 0.136296960 | 82.59 |
| 3 / baseline | 0.002041696 | 0.171837696 | 84.16 |

各阶段 Docker/原生比值再取版本中位数，新版/旧版为 0.8419，归一后的观察改善约 15.8%。这只是对基线波动的补充描述，不是对宿主负载的充分控制；两个阶段/版本不足以给出稳定的因果估计。改动同时包含缩短 virtqueue 锁作用域和直接执行 flock，也尚未拆分两者贡献。不能把本轮微基准下降写成整个 Docker 提速，更不能关闭关机超时缺口。

宿主负载不受本实验独占控制，样本不能代表完整 Docker 应用性能；GPU、POSIX 锁、共享 mmap 和通知等缺口仍保留。

## 取消与解锁竞争

`shared-cancel-race-v1` 增加真实 `ITIMER_REAL` 信号与外层解锁竞争：通过 `--cancel-race-iterations 200` 运行，原生和 Docker 各 200 轮。包括保持外层锁直到观察到 EINTR 的控制轮，以及 0、1、2、4 ms 解锁偏移。探针使用短周期定时器，避免高负载下信号先于 flock 进入导致控制轮永久等待；返回命令循环前阻塞、关闭并清空 SIGALRM，避免延迟信号污染下一条命令。

每次成功获锁都验证外层确实被排斥；每次 EINTR 都在**不发送内部 unlock** 的情况下验证外层可以获锁，避免把泄漏锁先释放再伪装通过。每轮随后校验普通文件读取，最终要求同时覆盖成功与取消结果。

两种模式分别出现 80 次获锁、120 次 EINTR，全部逐轮校验通过。原生检查 22/22，Docker 20/22，两项 POSIX 范围锁仍失败；进程退出码因此仍为 1。服务日志记录队列 completed=415、interrupted=122、peak=6、remaining=0，直接完成 12116 次、入队 209 次。64 个探针进程组正常清理，guest、网络和文件服务正常关闭，没有强制回收。输入哈希未改变。

这是单个重复等待者的定向竞争检查，不覆盖多客户端交叉取消、设备重置或异常断连，也不能证明历史关机超时已经解决。新探针 SHA256 为 `082292e65ed6ca0ecf4a369529b6767e19908197fb9a2d134e465eede1f18466`；ABBA 使用旧探针，其原始输入哈希保持不变。此轮计时不能合并进此前 ABBA 样本。
